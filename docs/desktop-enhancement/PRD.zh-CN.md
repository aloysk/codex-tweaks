## 第一章：产品概述

Codex Tweaks 桌面增强是一款官方 Codex 桌面体验工具箱，让经常在 Windows 上使用 Codex 的开发者调整阅读环境、查看可信状态并管理增强，而无需迁移会话或更换日常客户端。

产品价值来自减少日常使用摩擦。第一版不承诺提升模型推理速度；“速度”先定义为本地界面不因增强而明显退化。用户继续在官方 App 处理聊天、文件、工具与审批，增强只承担选定的辅助界面。

### 1.1 差异化对比表

| 功能 | 竞品 | 本产品 | 实现方式 |
|---|---|---|---|
| 配色之外的阅读体验 | 官方 Appearance 已支持配色与字体，未发现整套桌面通用换肤公开 API | 补足正文宽度、密度与静态背景，保持官方入口 | 先复用原生配色，再由独立包增量附加样式 |
| 持续增加日用功能 | Dream Skin 聚焦换肤；Token Overlay 聚焦外置状态 | 统一启停与恢复下管理少数自有功能包 | 复用 Codex Tweaks API v3，不另建插件商店 |
| 失败后继续工作 | 上游宿主已有清理能力，但关闭增强不等于关闭 CDP，Windows 重启有按进程名终止路径 | 区分“停用增强”和“普通方式重开”，明确剩余状态 | 收窄目标进程身份；重启由用户在合适时机手动完成 |
| 可信即时状态 | 不同监控项目混合使用日志、私有 HTTP 或 app-server | 首版只显示经核验的账户额度，来源和时效明确 | 借鉴 usage-overview 的现有状态读取；上下文另行验证 |

事实依据为本项目社区分析及其关键源码链接，取证日期为 2026-10-02。上述产品比较不是完整功能审计，也不是当前机器运行结果。核心上游及开发契约：<https://github.com/codex-tweaks/codex-tweaks>；额度参考：<https://github.com/codex-tweaks/codex-tweaks-usage-overview>；外置控件参考：<https://github.com/soleillevant0125/codex-token-overlay>。

### 1.2 三类用户画像

| 角色 | 核心目标 | 对现有体验最大的不满 | 愿意采用的关键功能 |
|---|---|---|---|
| 长时间阅读代码和回复的开发者 | 在不同屏幕上舒适阅读 | 字体之外的正文宽度、留白和背景难统一 | 一套可随时恢复的阅读布局 |
| 同时运行多个任务的个人使用者 | 决定何时继续工作、何时处理限制 | 额度含义和状态时效不明确，需要反复找入口 | 来源清楚、不会冒充当前会话状态的额度卡 |
| 愿意维护自己工具的开源参与者 | 逐步加上真实需要的能力 | 单脚本修改分散，更新后难判断何处失效 | 每个包独立开关，失败自动隔离，宿主 fork 差异可追踪 |

| 在范围内（及原因） | 明确排除在外（及原因） |

本机只读检测到 Codex Store `26.930.2377.0`、Go `1.27.0`、.NET SDK `10.0.112` 与 `10.0.401`、Node `24.11.1`、npm `11.18`、Windows SDK `10.0.26100`；未发现 mise。这里只证明已检测到工具及应用，不证明上游构建、注入或恢复通过；缺失工具待开发阶段按真实构建要求处理，本阶段不安装。合理推断：自有 Renderer-only 包能够降低凭据与后台进程处理范围。未知：当前安装版本与上游基线的实际兼容性、全部原生流程的焦点表现。

### 1.4 约束分层

| 硬约束 | 推荐默认 | 发挥空间 |
|---|---|---|
| 每个窗口、包、连接均明确归属；身份不明时停止作用 | 仅一个受支持 Codex 窗口先行；其他窗口显示不支持 | 状态图标、布局间距与信息层级 |

| 功能包退出后释放所拥有的 DOM、样式、监听与计时器 | CSS 和 DOM 采用包专属命名；读写隔离 | 与上游契约相容的内部代码组织 |

## 第三章：核心模块详细设计

### 第 3.1 节 连接、启停与恢复

#### a) ASCII 图

```text
+-----------------------------------------------------------+
| 连接与恢复                                                |
| Codex：已发现 · 窗口 1 · 兼容性待检查                      |
| 增强模式：未连接                                          |
| 操作：检查兼容性    查看启动指引                          |
|                                                           |
| 已连接时：停用全部增强    普通方式重开指引                  |
| 错误时：无法确认目标窗口。保持原生界面。  重新检查          |
+-----------------------------------------------------------+

未发现 --> 待连接 --> 检查中 --> 已连接 --> 停用中 --> 已停用
                     |           |                       |
                     +--> 不兼容 +--> 连接中断            +--> 等待普通重开
```

#### b) 交互流程

正常路径：用户打开管理窗口 → 确认官方 App 身份与目标窗口 → 用户确认已保存需要保留的内容、活动任务已结束，再按指引自行进入增强模式 → 只连接本机端点 → 探测必需能力 → 逐包激活 → 显示已连接。应用不能确认工作状态时不自动重启。启用配置先校验后应用，单包激活失败不使其他已验证包失效。

失败路径一：端口不存在或被占用 → 显示“尚未连接，可继续使用 Codex” → 保持关闭 → 用户处理启动条件后重试；不自行结束占用端口的进程。

失败路径二：目标路径、窗口或能力探测不匹配 → 显示“不支持当前版本或无法确认目标” → 禁止注入 → 可复制兼容性摘要；不能降级为盲目匹配进程名。

失败路径三：停止期间窗口已退出、清理调用失败 → 管理窗口保留“恢复待确认” → 重连同一目标可重试清理，或用户正常关闭后从官方入口重开 → 核验清理结果。仅关闭管理窗口不能显示“调试模式已退出”。

恢复语义分为两个动作、三项状态：**停用全部增强**先停止继续注入，再移除本项目注入效果，允许 CDP 仍存在；**普通方式重开**要求用户自行正常退出并从官方入口打开，核验调试端点不再由目标 App 提供。管理器分别报告“继续注入已停止”“页面清理已验证”“CDP 监听已关闭”，不能仅断开 WebSocket 就声称退出调试模式。检测不到端点时也应结合目标进程身份，不能把连接故障当作完整恢复的证据。

源码复核发现，上游全局停用路径可能忽略 `CleanupAllTargets` 的错误后仍报告 completed；本项目必须保留并呈现清理结果，清理失败归为恢复待确认。上游 `codexLaunchArguments` 当前总是加入 CDP 参数，未来“普通重开”若由宿主实现，需要明确的新启动模式；在此之前只提供官方入口人工重开指引。

#### c) 状态清单

| 状态 | 触发条件 | 视觉标识 | 退出条件 |
|---|---|---|---|
| 未发现 | 无匹配目标 | 灰色“未发现 Codex” | 用户打开官方 App 并重查 |
| 待连接 | 发现目标但无可用端点 | 灰色“未连接”及指引 | 用户启动增强模式 |
| 检查中 | 正在核验身份与能力 | 状态行进度，不遮挡 App | 探测完成或 5 秒超时 |
| 已连接 | 身份与必需能力通过 | 绿色文字及已启用包数 | 停用、断连或版本变更 |
| 不兼容 | 必需能力失败 | 橙色“不兼容”，启用禁用 | 适配更新后重新检查 |
| 连接中断 | 已连接目标消失 | 橙色“连接中断” | 明确重连成功或停用 |
| 停用中 | 用户停用 | 禁用重复点击 | 清理成功或 3 秒超时 |
| 已停用 | 所拥有资源清理确认 | “增强已停用；调试模式仍可能开启” | 用户启用或普通重开 |
| 恢复待确认 | 无法验证清理或普通重开 | 橙色说明与重试 | 获得同目标验证证据 |

#### d) 依赖关系

读取官方进程身份、目标窗口、CDP 可连接性和包能力；写入本项目连接状态、包开关与有限诊断。方向：身份探测 → 兼容性判定 → 包控制器 → 清理结果。源码中既有按进程名终止路径须在首个实现迭代收窄，面向日用版本不自动强杀或终止未知实例。权限失败保持未连接，不提权重试。

#### e) 待决问题

此处未解决：当前 Codex Windows 发行渠道能否在不影响活动任务的情况下可靠提供目标身份和 CDP 启动入口。技术验证 G1 决定采用现有启动流程的收窄实现，还是仅提供人工启动指引。产品默认选择后者，不承诺热开启调试能力。

舒适布局建议正文最大宽度 960 CSS px，紧凑布局 1120 CSS px；空间不足时保留至少左右各 24 CSS px，侧栏与原生输入高度保持原生约束。布局包只作用于已识别的普通正文区域，不隐藏工具错误、引用、差异、审批或表格横向滚动。具体宽度属于推荐默认，可按实际屏幕评估调整。

#### b) 交互流程

正常路径：选择布局或用户显式选择本地 PNG/JPEG/WebP → 检查类型、字节大小与解码尺寸 → 当前窗口预览 → 应用后保存本项目设置 → 界面提示“已应用”。原生明暗主题变化后重新计算遮罩与可读性，不改写原生配置文件。

失败路径一：非支持图片、文件超过 5 MiB 或任一边超过 4096 px → 内联提示具体限制 → 保持上一次有效状态 → 用户重选。SVG、远程 URL、动画图和目录扫描均不进入此路径。

失败路径二：正文容器无法识别或样式验证失败 → 回滚此次包拥有的修改 → 显示“当前版本暂不支持此布局” → 可继续使用原生布局。回滚只处理本项目拥有的节点和属性，不重置用户原生主题。

失败路径三：设置持久化失败 → 取消“已保存”提示 → 保留用户可见预览并提供取消 → 重试或恢复；下次启动只读取最后一次完整有效配置。

P0 包含布局与纯色背景，以及能力允许时的本次本地图片预览。**本地壁纸只有在 G2 证明 Renderer-only 选择、保存和恢复路径成立后才列入首版持久化交付承诺**；若能力不成立，首版明确省略持久壁纸，不能伪称完整实现或为此默认开启 Node。临时预览明确标识“本次窗口有效”，关闭后不承诺恢复图片。

|---|---|---|---|
| 原生 | 包关闭或恢复成功 | “原生布局” | 选择预览 |
| 待选择 | 本地图片开启但没有有效图片 | 图片占位和选择入口 | 选取通过验证 |
| 预览中 | 未保存的有效设置 | 预览条及取消 | 应用或取消 |
| 已应用 | 设置保存及视觉应用均成功 | “已应用” | 用户修改、停用或适配失败 |
| 读取失败 | 图片不符合约束 | 字段级错误 | 重选或关闭图片 |
| 保存失败 | 本项目存储写入失败 | “未保存” | 保存成功或取消 |
| 适配失败 | 目标容器或验证不通过 | “使用原生布局” | 更新适配并通过探测 |

#### d) 依赖关系

读取原生主题、视口大小、本项目设置和用户主动选中的文件；写入包拥有的样式、背景节点与本项目配置。文件输入只访问用户选择的素材，不读取任意目录。持久化应使用经实证的宿主包存储契约；该契约尚未核实时只定义本项目数据边界，不编造具体 SDK 方法。

#### e) 待决问题

此处未解决：Renderer-only 图片持久化与资源路径隔离的可用方式。G2 应核验配额、生命周期和多窗口读取表现；若需要 Node 或宿主通用文件权限，推迟壁纸持久化，保留布局与纯色背景。

### 第 3.3 节 可信账户额度卡

#### a) ASCII 图

```text
+-------------------------------+
| 账户额度                      |
| 5 小时：剩余 68%              |
| 每周：剩余 42%                |
| 最近读取 14:30 · 来源：Codex   |
| 详情：各窗口长度与重置时间     |
+-------------------------------+
| 陈旧：上次读取 68% · 2 分钟前 |
| 不可用：暂未取得额度数据       |
+-------------------------------+
```

这是账户级状态卡；“5 小时”“每周”等标签来自实际窗口长度，不能在所有账户上硬编码。剩余比例按 `100 - usedPercent` 计算并限制在 0–100；无值显示“未知”，不能填 0。重置时间来自源字段，使用用户本地时间呈现，本项目工作文档示例采用 SGT。

#### b) 交互流程

正常路径：确认宿主状态结构 → 读取合法额度字段与来源 → 标为账户级 → 规范化并显示 → 用户展开详情查看时间与来源。只读取宿主已取得的状态，不附加登录、不单独调内部 HTTP、不触发模型请求。

失败路径一：字段不存在、数值不是有限数、窗口身份不明 → 对应项显示“未知” → 记录字段级诊断 → 用户仍能使用 Codex；其他有效项继续显示。

失败路径二：切换账户、出现多个 active account scope、断连或数据时效不可确认 → 账户 scope 变化或歧义时递增本地 `scopeGeneration` 并撤下旧账户值，断连时使连接代次失效 → 显示“暂未取得额度数据”；仅在账户归属仍明确但本地采样超期时可保留标陈旧的旧读数 → 等到同身份合法快照再恢复。不能将“刚读缓存”表达成“服务端刚刷新”。

失败路径三：侧栏插槽不可用 → 停用内嵌卡片 → 管理窗口显示原因 → 用户可打开官方原生额度入口；不猜测替代 DOM 节点。

#### c) 状态清单

| 状态 | 触发条件 | 视觉标识 | 退出条件 |
|---|---|---|---|
| 获取中 | 第一次读取尚未完成 | 两行占位，最多 1 秒 | 得到结果或转不可用 |
| 有效 | 通过身份、结构与时效校验 | 正常文本，明确“最近读取” | 数据失效、断连或身份变化 |
| 部分未知 | 某个窗口缺合法字段 | 有效项保留，缺项写未知 | 得到完整合法快照 |
| 陈旧 | 连接与账户 scope 仍明确，但本地采样超期 | 灰色旧读数与经过时间 | 同 scope 的新合法快照或关闭卡片 |
| 不可用 | 断连、scope 歧义、无可信数据或适配不通过 | 撤下数字，显示“暂未取得额度数据” | 来源及身份恢复并通过校验 |
| 关闭 | 用户关闭模块 | 不占侧栏 | 用户重新开启 |

#### d) 依赖关系

读取当前官方 App 已有账户额度状态，转换为独立 `UsageSnapshot`；只写瞬时渲染状态和不含账号标识的诊断。参考包已核 commit 为 `2cfbec5563b5e0eb46cd146574d8986a14cc5e45`：它从 React Fiber 定位 QueryClient，读取 active 的 `rate-limit-status` Query Cache；多个 active account scope 时返回 null，不新增账户请求。这个保守降级值得保留，不能把“多个 scope”任取一个当当前账户。账户标识仅用于内存隔离，不持久化真实标识。来源未给服务端更新时间时 `sourceUpdatedAt` 为 null，必须展示“最近读取”而非“更新于”。

优先使用宿主订阅机制；无可信订阅时最多每 60 秒读取本地缓存一次，断连即标识，距最后成功采样超过 120 秒标陈旧。该时间阈值只表达本地观测状态，不能证明源数据服务器时效。`valid` 只表示结构与身份校验通过，不等于源数据刚更新；反复读取同一缓存只能更新 `observedAt`，不能更新 `sourceUpdatedAt` 或解除“源更新时间未知”的说明。事件触发的刷新不计入轮询频次，但仍需合并同一快照的重复渲染。

#### e) 待决问题

此处未解决：当前版本的账户识别、窗口长度与源更新时间能否稳定取得。G3 核验字段；如果无法可靠观察同一连接内的账户变化，则撤下额度数值并显示不可用，不能仅在重连时清空来规避该缺口。会话上下文、运行中与待审批提示属于后续范围，不能由账户额度反推。

## 第四章：超越竞品的差异化功能

这里的“超越”指本项目希望达到的组合体验，不代表已实现或所有其他项目都缺失这些能力。

### 第 4.1 节 可以验证的恢复

1. 竞品为何未必完整覆盖：基于公开信息的推断，换肤工具的主要边界是移除样式，退出调试模式还涉及进程生命周期；上游现有清理能力不能直接证明后者完成。
2. 本产品如何实现：分别展示界面增强、连接、调试模式三种状态；停用后验证包资源清理，正常重开后验证目标实例。推荐人工正常退出；自动重启只有未来具备准确身份与工作状态后再评估。
3. 交互流程：`停用增强 --> 确认界面恢复 --> 用户正常退出 Codex --> 官方入口重开 --> 核验普通模式`。
4. 风险与应对：验证不可得时保留“待确认”，不自动升级为强杀；管理器崩溃后以安全默认不自动重注入。

### 第 4.2 节 状态有出处，未知可见

1. 竞品为何容易产生缺口：基于公开信息的推断，不同监控项目最初服务单一日志或账户入口，接入桌面多窗口后，数据身份和新鲜度变成额外问题。
2. 本产品如何实现：数据模型带范围、读取时间、源更新时间与有效性；先账户额度，后当前会话上下文。图形表达必须保留文字含义。
3. 交互流程：`读取 --> 验证身份与字段 --> 有效值 / 部分未知 / 陈旧 --> 用户查看来源 --> 决定继续工作`。
4. 风险与应对：宿主更新改变结构时隐藏受影响字段，保留原生入口；不退回读取认证文件或内部 HTTP。

### 第 4.3 节 超预期机会

以下三个细节在基本闭环通过后按成本选择，不扩张 P0 承诺：

| 机会 | 结构性原因与实现 | 交互流程 | 风险与应对 |
|---|---|---|---|
| 临时查看原生效果 | 单次开关式工具常缺少对比状态；本项目已有可恢复样式状态 | 按住“原生对比” → 暂停本包视觉 → 松开恢复 | 不改配置；失焦时自动结束对比 |
| 恢复结果小卡片 | 跨生命周期恢复信息通常分散；统一管理器可以汇总 | 停用 → 展示已清理包数与仍待普通重开项 | 只展示已验证事实；未知写待确认 |
| 额度详情一句话 | 数据源与 UI 常各自实现；规范化模型可生成解释 | 展开 → “账户级；14:30 读取；源更新时间未知” | 不制造倒计时精度；字段缺失逐项说明 |

竞争原因均为产品推断，不能宣传成对其他仓库的事实判断。

| 浏览器 DOM / CSS / 文件选择能力 | 首批 Renderer-only 包 | 外观与显式素材输入无需另启文件服务 | 新增第三方依赖为 0 的设计目标，最终 bundle 待测 |

最大架构风险是官方更新使私有适配失效。应固定已验证的上游 commit，维护“Codex 版本 + 发行渠道 + Windows 架构 + 包版本”兼容矩阵；每包启动前探测自身必需能力。探测失败只关闭受影响包，失去目标身份则全部停止。支持声明以真机证据为准，编译通过不等于兼容通过。

宿主维护遵循上游 `AGENTS.md`：Go 是唯一共享业务后端，SwiftUI 与 WinUI 保持薄视图；生成 contract 由权威定义生成，不手改产物。Windows 优先决定首批运行验收平台，不允许将恢复、设置或错误语义分别复制进两种原生 UI。修改共享契约时，仍需保持两端消费方式一致并执行受影响的构建/契约检查。

Git 分发的自有功能包按“一包一仓库”组织，包成立并需要发布时再建对应仓库；当前不批量创建空仓库。宿主 fork 保留原始结构和上游同步路径，研究与规格集中于 `docs/desktop-enhancement/`。

**可替换技术原则：** 默认沿用上游栈，不为外观功能替换宿主。未来若 CDP 路线在目标版本不可持续，可评估 Token Overlay 式外置伴侣；切换须明确放弃哪些内嵌外观能力，不能悄悄把产品改成另一个聊天客户端。不可变的是数据含义、原生输入与审批边界、功能独立停用、可验证恢复、最少权限和本地数据归属。自有包内部是否采用框架可以调整，但不得新增无必要的 Node 进程或网络来源。

fork 初始化的顺序是：先取得上游 fork 或保留上游历史的本地克隆 → 设置 `upstream` → 固定基线 → 在自己的工作分支增加研究、PRD 与准备文档。无需先新建空仓库再把它“变成 fork”。本轮已完成 fork，后续状态以 `UPSTREAM.md` 为准。

发布是另一个明确边界：现有更新源仍指向上游 `UpdateRepository`，packId 使用 `com.crzhichen.CodexTweaks.$architecture`。发布自己的安装器前必须确定独立更新源、包身份、数据目录及与上游并装策略，验证不会覆盖上游安装或错误更新。本阶段只记录这些前置要求，不改更新配置、不发安装包，也不把本地构建成功等同于可公开发行。

正文、代码与错误提示按 WCAG 2.2 的对比度标准检查：普通文本至少 4.5:1，大字至少 3:1；不能仅因遮罩大于某值就宣称合格。这里的大字按标准定义，不能自行把字号较大的 UI 文案都算入宽松阈值。参考：<https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html>。高对比度模式默认关闭壁纸；系统减少动画偏好下去掉非必要过渡。首次进入默认原生布局和无背景，用户自行选用。

## 第九章：开发优先级

## 第十章：性能指标

以下全部是**设计目标，尚未实测**。固定同一机器、同一官方版本、同一会话和窗口尺寸，增强关闭作为基线；记录硬件与系统版本。启动类至少重复 10 次，交互类至少 100 次；首轮样本用于校准目标，调整需保留理由。模型首字或生成速度属于外部依赖，不作为本项目提升承诺。

| 指标名称 | 目标值 | 测量方法 | 劣化阈值 |
|---|---:|---|---:|
| 按钮点击至本项目设置可交互 | p95 ≤ 200 ms | 浏览器 performance 标记与屏幕录制核对 | p95 > 500 ms |
| 配置应用至首帧可见 | p95 ≤ 150 ms | 设置提交和 requestAnimationFrame 标记 | p95 > 300 ms |
| 全部首版包激活耗时 | p95 ≤ 1000 ms | CDP 已连通后至所有包完成，不计 App 启动 | p95 > 2000 ms |
| 停用至所有自有资源清理 | p95 ≤ 1000 ms | 资源登记表、DOM、监听与计时器检查 | > 3000 ms 进入恢复待确认 |
| 闲置 CPU 增量 | ≤ 1 个百分点 | 同场景 10 分钟平均，增强开关对照 | > 2 个百分点 |
| 内存增量 | ≤ 120 MiB | 全部相关进程 working set 中位数，10 分钟采样 | > 200 MiB |
| 长会话滚动帧耗时增量 | p95 增量 ≤ 3 ms | 同一 500 条消息测试会话，60 秒 trace | p95 增量 > 8 ms |
| 页面主线程新增长任务 | 60 秒内 ≤ 1 个超过 50 ms 的任务 | Performance trace 按本项目脚本归因 | 60 秒内 > 3 个 |
| 静态图片输入限制 | ≤ 5 MiB 且单边 ≤ 4096 px | 导入前大小校验、解码后尺寸校验 | 任一超限拒绝，不降级绕过 |
| 本地额度 fallback 轮询频率 | 最多 1 次 / 60 秒 | 仅计兜底定时读取；事件订阅刷新不计为轮询 | 超过 2 次 / 60 秒 |
| 连接中断后撤下数字并显示不可用 | ≤ 2 秒 | 断开目标后录屏与状态日志比对 | > 5 秒 |
| 启停循环资源增长 | 20 次后自有 DOM/监听/计时器归零 | 激活/清理登记及堆快照对照 | 任一持久增长或残留即失败 |

测试会话用合成内容，不把真实用户对话写进 fixture。超过劣化阈值先关闭受影响包并定位；性能目标调整须区分机器基线与实现缺陷。不能用禁用 GPU、缩减原生内容或更改历史来满足指标。

### e) 验收剧本

**验收剧本 1：连接与恢复。** 你在 Windows 11 x64 的已记录版本上，先使用空闲测试实例按人工启动指引进入可连接状态，再输入一段未发送的合成草稿。启用布局和额度包，停用全部，检查草稿内容未变且未发送、自有 DOM 与监听归零。普通重开前由用户显式保存或撤销测试草稿，再正常退出并从官方入口重开，核对普通模式。本产品不承诺官方跨重启保存草稿的行为。使用前后截图、资源计数、目标身份摘要和调试端点结果分别验证停止注入、页面清理与监听关闭；任一状态未知必须记录为待确认。

**验收剧本 2：阅读与素材失败。** 你打开合成的长会话和代码/差异/审批样例，在原生、舒适与紧凑之间切换，再模拟容器探测失败。应恢复原生且保留所有重要信息。若 G2 通过，再导入合法图片、超过 5 MiB 文件和伪装扩展名文件；后两者应被拒绝且保留上次设置。用 100%/125%/150% DPI 截图、对比度检查、配置文件与清理记录验证。

**验收剧本 3：额度含义与失效。** 你将实际有效宿主额度与规范化输出逐项对照，再用测试 fixture 模拟缺字段、非数值、账户变化和断连。有效项应保持账户级语义，未知不显示为 0%，旧账户值不得继续显示为有效，读取时间不得冒充源更新时间。用最小映射测试、画面截图及不含账户标识的状态序列验证；测试 fixture 不替代真实账户有效显示证据。

**验收剧本 4：快捷入口与焦点。** 你在原生输入框保留草稿，使用鼠标和 Tab 打开增强设置，关闭后观察焦点；再在设置打开期间切换会话、重复点击入口并使原焦点元素消失。应仅有一个设置实例、没有发送或改写草稿、不会把焦点跳到另一个聊天输入框。用事件记录、逐字符草稿对照和录屏验证，覆盖中文输入法组合输入。

**验收剧本 5：兼容失败与性能。** 你连续启停 20 次，模拟不支持的包能力，再测相同合成长会话在增强开/关下的 60 秒滚动与 10 分钟闲置资源。失败包应隔离，原生界面可继续使用，自有资源清理到零；将第十章指标的实际值与阈值逐项记录。用 trace、进程采样、资源计数和版本矩阵证明结果。超过阈值时列为未通过，不以主观“感觉没问题”替代证据。
