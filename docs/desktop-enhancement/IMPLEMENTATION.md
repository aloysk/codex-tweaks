## 实施顺序

### 先建立可用的开发环境

读取根 `AGENTS.md`、PRD 的 AI 速读卡与第十一章，再确认上游基线是否发生变化。使用新的功能分支或必要的隔离 worktree；保留本准备提交和未提交的用户工作。

优先运行不触碰真实 Codex 的 Go 单元检查与生成文件校验。Windows 构建采用上游现有脚本；`mise run verify` 含 macOS 与 Xcode 步骤，应在对应主机运行。需要依赖下载、输出目录更新或本地工具恢复时，先读脚本的实际副作用，再使用任务范围内的环境。

在第一次启动可安装 fork 前，确定独立的应用身份、数据目录和更新策略。开发包默认不自动更新、不迁移上游数据。先做 mock 单元检查不需要把上游 namespace 全部重命名；开始并装测试时才完成实际隔离改动并验证。

### G1 连接与恢复

**目标：** 用户能够明确知道连到了哪一个 Codex 实例，并能停止增强和验证恢复结果。

代码落点：`backend/internal/core/platform.go`、`platform_windows.go`、`cdp.go`、`controller_runtime.go`、`controller.go`、状态类型、对应 tests；必要时更新 RPC、Go Presentation 源和原生 Overview 视图，然后生成共享契约。

按以下顺序实现：

1. 用已确认的完整路径、PID 和进程启动身份锁定目标。模拟同名无关进程、多实例、目标退出和 PID 重用。
2. 明确普通启动与增强启动。取消、超时和无法确认目标时保留当前工作；不要自动按进程名结束所有实例或强杀。
3. 逐目标汇总 cleanup 结果，将“停止继续注入”“页面清理已验证”“CDP 监听已关闭”作为不同事实；失败保留可解释的状态和重试入口。
4. 先用合成 renderer 和 mock 进程测试上述行为，再在专用测试实例中验证。需要退出官方实例时，由用户先保存工作并主动继续，不能以测试脚本代为确认。

**通过证据：** 无关进程未受影响；取消后草稿与运行任务不变；故意制造的 cleanup 失败不会显示恢复完成；普通启动后目标实例不带 CDP 参数且对应监听消失。关闭 Tweaks 的 WebSocket 不能算最后一项通过。

**关口未过：** 停在可诊断的未连接或恢复未完成状态，不开始往日用窗口加载新功能包。

### G2 最低权限外观

**目标：** 一个 Renderer-only 包能提供可恢复的阅读布局和静态外观。

实现优先放在自有功能包，宿主只做必要适配。先用本地目录／ZIP 验证，不创建主题商店、云账号或一组空功能包仓库。

先完成文本宽度、界面密度、对比度和专注布局。静态图片由用户明确选择；上游 `custom-background` 包声明 Node，不能直接通过选择本地模式获得 Renderer-only 权限边界。裁剪实验包需移除 Node 入口与远程图片流程。持久图片存储只有通过能力验证后才开放；没有可信持久化路径时明确标为当前会话预览，并按 PRD 的降级范围交付。

**通过证据：** 浅色／深色、高对比度、125%／150% 缩放、窄窗和审批弹窗可读；重复启停 20 次没有重复 DOM、观察器或计时器；失配仅停用该包；图片功能不发外部请求。

**关口未过：** 回退到已验证的配色／阅读布局，关闭失败的图片或设置页适配，不扩大权限以掩盖能力缺口。

### G3 额度真实性

**目标：** 展示当前账户已有额度信息，允许明确的未知状态，不把账户数字当成线程用量。

研究起点为 `codex-tweaks-usage-overview@2cfbec5563b5e0eb46cd146574d8986a14cc5e45`：从宿主现有 active `rate-limit-status` Query Cache 读取，多账户 scope 歧义时返回无数据。这是私有结构适配样本，不是 API v3 的通用数据接口。

**通过证据：** 账号切换、两个窗口、未加载 query、网络离线与旧缓存都遵循 PRD 的状态与新鲜度规则；多个 active scope 不猜测取值；无额外账号请求、无认证文件读取、无为了刷新额度发送模型 prompt。

**关口未过：** 显示“额度暂不可用”及原因，保留打开原生用量入口的选择。数据缺失场景下不显示上次账户的数字。当前线程 token 与上下文占用属于后续阶段，先验证选中线程身份再开发。

### G4 入口与整体验收

**目标：** 一个明确的“增强设置”入口能帮助用户管理本项目功能，且不干扰原生输入和导航。

优先使用已注册的原生设置入口。`ui.settingsSections` 只公开注册等能力，侧栏按钮能否导航到指定设置页须独立验证；注册成功不代表存在可调用的打开方法。导航不成立时取消侧栏快捷按钮；注册也失败时提供人工打开宿主管理窗口以停用或诊断的指引，不宣称那里已经能编辑尚未实现的自有包设置。第一版不把自动填充提示词、发送、审批或跨任务批量操作混入该入口。

**通过证据：** 空草稿、多行草稿、中文 IME 组合输入、键盘选择、长对话、不同窗口下都不丢内容、不误发消息；焦点返回符合 PRD；减少动画与高对比度可用。随后按 PRD 第十章，用同机同场景的未增强基线完成性能比较。

**关口未过：** 关闭有问题的快捷能力，保留宿主可达的设置入口；不通过页面重载或重启来掩盖输入状态问题。

## 首个可安装版本的交付条件

G1 至 G4 通过只证明开发场景，实际分发还需要：

- fork 的 package ID、更新源、应用身份、数据目录和卸载归属已隔离；原版和 fork 能按既定策略共存。
- Windows x64 完成真实安装、升级、卸载和重启后的恢复；ARM64 只在真机验证后声明已验证，交叉构建只证明产物架构。
- 共享 Go 和 Presentation 修改满足上游双端要求；Windows 优先不能变成在 C# 复制业务逻辑或无意破坏 macOS。
- 功能包可独立停用；至少有当前支持版本与失配版本的处理证据。
- 发布内容只包含代码、许可、必要资源和脱敏说明。用户图片和上游商标／素材权限需要按实际分发内容核实。

这些是未来发布条件，本准备阶段没有创建标签、执行 release workflow 或发布二进制。更新源仍保留原值，所以当前 checkout 不应被当作已经隔离的可安装 fork 产品。

## 接续开发时的第一条任务

你应从 G1 的纯函数和 mock 测试开始：先确认 Windows 目标进程身份与 cleanup 失败传播，再设计 Go 状态契约。把每次变更限定为一个有可观察验收结果的能力。完成后更新证据状态，只有受影响关口通过才进入下一个依赖步骤。尚未执行的关口保持“未执行”，不要用 PRD 里的验收目标填入实际结果。
